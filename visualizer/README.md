# Visualizer scenes

The visualizer draws scenes in Rune's own format and nothing else. Rune ships seven (Armillary, CRT Wall, Emoji Tunnel, Growth, Neon Street, Paperclip, Torii Sea), compiled into the binary on every platform. More come from folders the user picks.

## Where scenes come from

- The built-in scenes are the folders of `visualizer/scenes/` (MPL-2.0 like the rest of Rune). `build.rs` walks them, sorted and without hidden files, and embeds every file with `include_bytes!`, images included (`scene::Source::Embedded`). A scene is added by putting a folder with a `scene.toml` there. Armillary is shown first and when the user removes the last scene folder. An embedded scene is read from memory and never reloads. They are used for the light and the dark appearance alike.
- Scene folders are added and removed in Settings > Theme, any number of them. A folder inside them with a `scene.toml` is one scene; the folders in between, also subfolders, are searched, and a scene's own contents are not. The built-in scenes and the folder scenes all take part in next, previous, random and the automatic switching, once per scene even if folders overlap. A folder scene with the same name as a built-in scene (the folder's name, as the menu shows it) does not replace it: both are listed and both take part, so a built-in scene can be copied to a folder and edited there with hot reload. Hidden folders (names starting with `.`) and symlinked folders are skipped. A folder that cannot be read is skipped and reported in the status error. In the preset list a built-in scene has the path `builtin:<name>` and no group; the cover wall's menu lists them first, directly in the scene submenu.
- Setting the folders (`Visualizer::set_preset_dirs`) empties the list and the history. With no scene left in the folders, a running visualizer changes to Armillary; otherwise the app asks for a random scene.

## Scene switching

The rules follow MilkDrop 2's defaults (Nullsoft, BSD-3), without the ratings:

- Random picks are uniform. The last 64 loaded scenes are kept. Previous walks back through them (and does nothing at the start). Next walks forward again after going back, otherwise it loads a new random scene. Random always loads a new one and drops the way forward.
- The visualizer switches by itself once per song, never on a timer or at a place in the music (`src/switching.rs`). A song is a playing file: the scene on screen stays while the same file plays, however long, through pauses, seeks and a repeat of the same file. When the file changes, the next scene is built in the background while the old one keeps drawing, and shown as soon as it is built. If the new song is silent then (the gap between tracks) the scene fades through black; otherwise it switches at the next followed beat, or the next hit without a followed beat, through one of the scene's strong transitions (a fade if it has none), and after 2 s at once if none comes. The next scene is a random pick among all scenes, never the one on screen unless it is the only one. With no file (nothing playing, an online stream) it never switches. When the visualizer opens, its first scene is chosen as before; the first song change after that switches. A scene loaded by hand replaces the one built ahead, and a locked scene (context menu) stays across songs until it is unlocked; while it is locked or the context menu is open, a song change is not noticed.

## Writing scenes

The scene on screen is reloaded whenever its files change, so a scene can be written in any editor while it plays. Put it in a folder of its own, add that folder in Settings > Theme, and lock the scene from the cover wall's context menu so the automatic switching leaves it alone. A save that does not load shows the problem in the visualizer's corner until the next save fixes it.

## Scenes in Rune's own format

A scene is a folder with a `scene.toml` (nothing inside it is scanned for other scenes). A scene is written in WGSL only. `update()` runs once per frame on the GPU and keeps whatever `struct State` declares. Its passes draw into HDR buffers that can keep the last frame. The runtime adds bloom, AgX tone mapping, chromatic aberration, vignette, grain and dithering. The scene reads the music as named fields: beat, bar and section with how many of each went by since the last frame, the chart's energy, onsets and leading stream, a spectrum and the waveform. Parameters with labels, ranges and units are declared in `scene.toml` and appear as `params.<id>`. `frame.accent` is the app's accent colour (which follows the system, the user's choice or the cover), so a scene can take its colours from it. A scene that declares `covers = true` in `scene.toml` also sees album covers from the user's library: `covers` is a 1024x1024 texture (sRGB, with mips) of 8x8 cells of 128 px, row-major from the top left, each cover scaled to fill its cell (the middle square of it). Cell 0 is the cover of the track playing now and stays transparent if it has none, cells 1.. are random covers; `frame.covers` is how many cells from the first are valid (0 when the library has no covers, else at least 1; cell 0 counts even when empty). The scene sees one clear texel and `frame.covers == 0` until the first covers are loaded. The random covers are looked up and decoded in the background when such a scene loads and stay while the track changes; then only cell 0 is replaced (also in the background), so nothing blocks a frame and covers do not all change at once; other scenes cost nothing.

- Images are `[[asset]]`s (PNG or JPEG, `asset_<id>` in WGSL, with mips). `linear = true` marks data such as a distance field, which must not be decoded as sRGB.
- Code that several passes share goes in files listed as `common = [...]` in `scene.toml`; every pass includes them (the update does not).
- Frames should keep to the frame rate (60 fps) also on phones, so the runtime adapts the quality. It measures how long each frame takes on the GPU (timestamp queries where the GPU has them: Apple GPUs, DirectX 12, Vulkan; else the time from submitting a frame until it is done) and counts the frames that arrive per second. It only lowers when both say so: the frame rate is under 95 % of the target and the average GPU time of the last half second is over 85 % of a frame's time. At the target frame rate it never lowers, whatever the GPU time says (a phone's GPU clock drops with the load, and the compositor shares the GPU). It lowers one step at a time, judging each over a second: if the frame rate did not reach the target or rise by 5 %, the step is undone and lowering stays off for 30 seconds (doubling each time), so a scene whose cost does not follow the resolution stays at full quality. First it lowers the internal resolution: `[render] scale` (default 1) is the most it is, and it goes down to half of that in steps of 0.1, all buffers with it (their `scale` stays against the internal resolution, and those that keep the last frame carry over, stretched). Only at half does it lower `frame.quality`, from 1 in steps of 0.25 down to 0; a scene may read it to take fewer ray-march steps or samples, and one that does not read it looks as it always did. Going back up, at the target frame rate, the quality comes first, then the resolution, after a few seconds with clearly room and only where the estimate says the frame still fits; a raise that leaves the frame rate under the target is undone and makes the next wait twice as long, so nothing flickers. A new scene starts at full. `frame.resolution` is the internal resolution and can change from one frame to the next, so sizes in pixels should be worked out from it each frame. Every 10 seconds the log says the frame rate, how long the scene's frames took on the GPU (average and worst), the resolution factor and the quality, and a line says when a step was undone for not helping.
- `docs/scenes.md` is the reference for the scene format: the folder, every key of `scene.toml`, the update and the state, and everything a scene's WGSL gets. `docs/music.md` says what the music fields mean and how scenes bind them.
- `src/scene/manifest.rs` is the reference for `scene.toml`, `src/scene/wgsl.rs` for what every shader sees (the prelude), and `src/scene/stdlib.wgsl` for the `rv_*` functions.
- The scene on screen reloads when its files change (a built-in one never does). When only parameter defaults changed, nothing else is rebuilt. When `struct State` reads the same, the state carries over. Errors name the file and line.
- Switching between scenes cuts.
- `cargo run -p visualizer --example snapshot -- <dir> [scene folder]` renders a scene to images, Armillary without a folder. `SNAPSHOT_SIZE=1920x1080` sets the size, and the frame rate is printed.

## The beat

Rune runs a beat tracker on the music (`src/rhythm.rs`) and hands a scene its findings as named fields: the tempo, a beat clock, how clearly the music has a beat, onsets of three bands (30 to 160 Hz, 160 Hz to 4 kHz, 5 to 16 kHz) and the loudness of the last second against the last 20 seconds. `cargo run -p visualizer --example beat_track -- <rate> <channels>` runs the tracker over raw `f32` samples from stdin.

On top of the raw findings the runtime makes signals that are meant to be read instead of `bpm`, `feel` and `energy` (`src/scene/signals.rs`): `tempo` (bpm, never 0), `clock` (a beat clock that always runs, whole numbers divisible by `meter` are downbeats), `meter`, `locked` (how sure the beat is), `drive` and `intensity` (the slow and the faster energy), `cues`/`cue`/`cue_in` (big moments), `notes`/`note` (melody notes), `band_low`/`band_mid`/`band_high` and `impacts`/`impact` (hard hits inside a section). Built-in scenes read these. The full reference is `docs/music.md`.

## The song's chart

A chart is what an analysis of the whole file found: its beats, bars, sections and onsets. The player tells the visualizer which file plays and where (`Visualizer::set_playback`, with every progress report) and how to open files (`Visualizer::set_fsio`, once), and the visualizer analyses the playing file itself when it starts, in a background thread (`chart_analyzer`, a second or two for a song; no cache, nothing is read or written). A new track cancels the analysis of the one before, and online tracks (no path) are not analysed. Until the chart is ready, and when there is none (the analysis failed, or an online track), scenes have no beat and move on what the live analysis hears: its onsets, levels and how fast the music feels. `cargo run --release -p visualizer --example chart_at -- <audio file> [seconds...]` prints what scenes would see.

With a chart, the tempo, beat clock and beat confidence come from its beats (the count is then beats since the song's first beat, and jumps on a seek), and the scene also sees bars, the meter, sections (index, label, loudness, time in and left, what comes next), onsets of the percussive low, mid and high bands, pitched sounds and phrases, the leading stream, and loudness, brightness, percussiveness and pulse. Without one, these read 0. `src/scene/inputs.rs` is the reference for the fields.

Scenes are only told of a beat when there is one to trust, and only the chart has one. `bpm`, `beat` and `beat_confidence` come from the chart's beats when it has them; a chart without beats (no steady pulse in the whole song) is the verdict, and they read 0 for the song. Without a chart they read 0 too, whatever the live tracker thinks: its tempo is often off by half or double, and a beat that does not match what is heard looks worse than none. So `bpm > 0` always means there is a beat. A scene that needs the beat grid reads `beats`, `bars` and `bar` and never sees them tick without a beat.

For music without a beat `hits` (how many moments to move on since the last frame) and `hit` (an envelope: the moment's strength, fading with a time constant of 0.2 s) stand in. Every trusted beat is a hit of strength 1; with a chart without beats the hits are its onsets of the leading stream (the harmonic one when none leads) and phrase starts, no weaker than 0.3; with no chart they are the live onsets (kick, snare or hat) that rise above 0.5. Two hits made of onsets are at least 0.25 s apart, and a seek, a stall or the chart arriving fires none. `hits - beats` is the number of hits that were not beats. Speeds that came from `bpm` use `feel` (about 3 Hz for a ballad to 7 for drum and bass) when `bpm` is 0.

## How frames reach the screen

The render thread draws each frame on the GPU, and the hub hands it to Flutter as a texture it registers with the engine (`flutter-texture`). The status reports the way it took (`transport`) and the adapter it renders on.

- macOS (`iosurface`): frames are drawn straight into IOSurface-backed pixel buffers, which Flutter shows without a copy.
- iOS (`iosurface`): the same path as macOS. The runner hands the registry of its plugin registrar (`FlutterPluginRegistrar.textures()`) to the hub. The iOS simulator may refuse IOSurface-backed Metal textures; the visualizer then falls back to `readback`, whose BGRA frames are copied into a pixel buffer.
- Windows (`dxgi-shared`): frames are drawn straight into DirectX 12 textures shared through NT handles, which Flutter opens on its own device (through ANGLE) without a copy. That only works on the adapter Flutter renders on, so the app tells the visualizer that adapter's LUID before it starts (the hub reads it from the engine through `flutter_texture::capabilities`), and the visualizer renders there. The hub registers the texture itself with the engine's C API (`flutter-texture`, no C++ bridge in the runner): a GPU surface texture while the transport is `dxgi-shared`, and a pixel buffer texture when it is `readback`. When the transport changes while running, the hub registers the other kind, tells Dart its id, and unregisters the old texture once Dart shows the new one. If the engine refuses the GPU texture (it has no ANGLE), the visualizer falls back to reading frames back. Without a DirectX 12 GPU (a virtual machine without GPU acceleration, a very old GPU) wgpu would draw with WARP, Windows' software renderer, whose shader compiler crashes the process on most scenes, so the visualizer does not start there and says so in the status.
- Linux (`vulkan-shared`): frames are drawn straight into Vulkan images whose memory is exported as file descriptors, which the hub imports into Flutter's OpenGL context (`GL_EXT_memory_object_fd`) as textures without a copy. That only works on the GPU and driver of that context, so before the visualizer starts the hub reads their UUIDs from a context like Flutter's (`flutter_texture::capabilities`, on the GTK main thread), and the visualizer renders on the Vulkan device with the same UUIDs. After each frame the image is released to the external queue family and a semaphore of its own is signalled, which the hub waits for (`GL_EXT_semaphore_fd`) before Flutter samples the frame. The hub registers the texture itself (`flutter-texture`, an `FlTextureGL` subclass made from Rust, no C++ bridge in the runner); the same texture uploads read-back frames, so falling back to `readback` keeps the texture id.
- Android (`surface`): the texture is a `SurfaceProducer` of the engine's `TextureRegistry` (`flutterEngine.renderer`, which `MainActivity` hands to the hub through JNI), and the visualizer presents each frame into the native window of the producer's surface with a Vulkan swapchain. On API 29 and later the swapchain's images are the buffers of the producer's `ImageReader`, which Impeller samples without a copy; nothing is handed over frame by frame. The hub registers the texture before the visualizer starts, so that the adapter is one that can present into its window; on a resize it gives the producer the new size and the visualizer the producer's new window. Read-back frames would show nowhere on Android, so a window the visualizer cannot present into is an error in the status rather than a fall back.
- The fallback on the other platforms (`readback`): frames are drawn into an offscreen texture and copied into a buffer that is mapped for reading; Flutter uploads the pixels again. With rows that are a multiple of 64 pixels wide, Windows hands over the mapped buffer without copying it on the CPU; Linux uploads the mapped rows as they are whatever their width.

Frames are read back instead when `RUNE_VISUALIZER_READBACK=1` is set (or a test asks for it), when the zero-copy targets cannot be created, or when they fail while running (the switch shows in the status). On Windows also when the app could not tell Flutter's adapter, or when no DirectX 12 adapter has its LUID; the visualizer then lets wgpu pick an adapter, preferring a high-performance one, as on the other platforms. On Linux also when Flutter renders in software (`FLUTTER_LINUX_RENDERER=software`), when there is no EGL display for GTK's (Wayland or X11) display, when its OpenGL context lacks `GL_EXT_memory_object`, `GL_EXT_memory_object_fd`, `GL_EXT_semaphore` or `GL_EXT_semaphore_fd` or runs on several GPUs, when no Vulkan adapter has its device and driver UUIDs, when that adapter cannot export memory and semaphores as file descriptors (or has no Vulkan 1.1), and, from then on until the app restarts, once OpenGL failed to import a frame (the visualizer then switches to `readback` while running).

- `RUNE_VISUALIZER_BENCH=<seconds per scene>` turns on benchmark mode: the render thread ignores the scene asked for and goes through every built-in scene in order, each for that many seconds (half with the adaptive quality frozen at full level, half with it on, starting from full; the first second of each half does not count), then starts over. Each half ends with one line in the log, `Visualizer bench: scene=Growth phase=full frames=118 fps=59.3 gpu_avg=14.2 gpu_p50=14.0 gpu_p95=16.8 gpu_max=21.0 factor=1.00 quality=1.00 size=1170x2532` (GPU times in milliseconds; `factor`, `quality` and `size` are where the scene ended up), and every pass ends with `Visualizer bench: cycle done`. The first line says whether the GPU times come from timestamp queries (`timestamps=yes|no`). On an iPhone, start the app with `xcrun devicectl device process launch --console --environment-variables '{"RUNE_VISUALIZER_BENCH":"20"}'` and grep the output for `Visualizer bench`. `RUNE_VISUALIZER_BENCH_SCENES=Growth,CRT Wall` measures only those scenes.

The zero-copy paths keep the last three published frames, and every frame someone still holds, away from the renderer, because Flutter may sample a frame after it let go of it. With every target in use the renderer skips a frame instead of drawing over one.
